# Security Specification

## Data Invariants
1. A user's preference document must be stored exactly under their user ID (`userId == request.auth.uid`).
2. The user can only read, write, or update their own preference document.
3. No user can access or write to another user's preferences.
4. Timestamps must be validated against `request.time` when updated.
5. Every field must respect strict types and bounds to prevent denial-of-wallet resource bloat.

## The Dirty Dozen Payloads (Security Test Cases)
We want to ensure that each of these malicious payloads is blocked by our Firestore rules:

1. **Anonymous Write Access**: Trying to write or create a document without a valid Firebase Auth session.
2. **Identity Spoofing**: Trying to write a document under `user_preferences/hacker_uid` where `ownerId = innocent_victim_uid`.
3. **Foreign Profile Writing**: Trying to write a document under `user_preferences/victim_uid` using a valid user token for `hacker_uid`.
4. **Invalid Type for Temp Unit**: Setting `tempUnit` to a random string like `"Kelvin"`.
5. **Invalid Type for Dark Mode**: Setting `darkModeSetting` to `"neon_rainbow"`.
6. **Malicious Giant Array (Denial of Wallet)**: Injecting an array of 5000 random cities into the `cities` field.
7. **Malicious ID (XSS/Poisoning)**: Creating or requesting a document ID containing special path injection characters like `../admin/rules`.
8. **Spoofed Autogenerated Status**: Attempting to bypass the security configuration to read a system path.
9. **Tampered Timestamp**: Creating an preference with a hardcoded `updatedAt` value in the past or future instead of `request.time`.
10. **Bypassing Fields Validation**: Sending a payload missing required fields like `tempUnit` but hoping a relaxed update rule preserves it.
11. **Spoofing email_verified**: Accessing data when authenticated but unverified (if required, or checking standard authentication context).
12. **Blanket Query Scrape**: An authenticated user attempting a blanket `getDocs` list query on `user_preferences` without specifying their own UID constraint.

## Test Strategy
All these attempts will return a standard `PERMISSION_DENIED` since:
- `user_preferences/{userId}` matches exactly `{userId}` with `request.auth.uid`.
- Writing triggers validation checking `ownerId == request.auth.uid`.
- Read and write rules strictly verify resource ownership.
